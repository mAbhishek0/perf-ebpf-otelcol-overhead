# LESSONS.md — what the Platform S work learned the hard way

Platform S (the 192-core server) ran 440 runs through the pipeline in [../docs/drafts/nginx-perf-pipeline-server/](../docs/drafts/nginx-perf-pipeline-server/) and hit most of the problems a pipeline like this can hit. The server results and plans are now side notes (laptop data is the priority), but the fixes are not: every laptop benchmark script must be written against this list. Each item gives the problem, how it was solved, what the laptop should do (**Laptop:**), and a source (file under the server tree unless a path is given, or a commit hash).

Compiled 2026-10-14 from SERVER-NOTES.md, the server README, all results docs, LEARNING.md, git history and script header comments. Two items are **inferences, not documented findings**, and are marked as such; both need checking on the laptop. Add new lessons here as they turn up, and mark any item a later finding overturns instead of deleting it.

## Host configuration (SMT, boost, governor, cpusets, sysfs that lies)

- **Boost must be written before SMT is disabled.** On S, writing boost=0 after SMT-off was silently ignored: every sysfs file read back 0 and 2.25 GHz, but turbostat measured 3724 MHz. Writing boost while SMT was still on worked and held after SMT-off; 03 was reordered. **Laptop:** governor and boost first, then SMT, with a comment saying the order is load-bearing. The quirk may not exist on Zen 2, but only measuring tells. (SERVER-NOTES §4.1, `5aa7313`)
- **A read-back does not prove a setting took.** 03 ends by loading one workload core with `taskset … while :;` for ~4 s and comparing `scaling_cur_freq` against `scaling_max_freq`, writing `state/clock_ceiling_verified.env`; it warns rather than fails. **Laptop:** keep the measured check and cross-check once with turbostat. Base clock is 2.9 GHz. (03_configure_env.sh, README "Base-clock confirmation")
- **Per-run clock check.** In the `/proc/stat` sampler loop, read each workload core's `scaling_cur_freq` once a second; judge on min/max, not the mean, with 5% tolerance, because amd-pstate reads ~1% high (APERF/MPERF). Record governor and boost beside the verdict, carry the verdict into `run_notes`, and note when the check could not run. **Laptop:** keep it; amd-pstate-epp is in active mode, so re-derive what "base" reads before trusting the band. (`1caf82b`, 00_lib.sh `summarize_cpu_freq`)
- **Why boost must be off.** With boost on, a traced run draws more power and clocks lower than its baseline — a one-directional bias on the headline number. Boost-off cut S's traced-vs-baseline mean-clock difference to 0.015%. **Laptop:** matters more on a thermally limited laptop; also stop TLP, set platform profile `performance`, log RAPL and temperature every run. (FIRST-RUN-RESULTS, [README.md](README.md))
- **Verify the SMT write by CPU count, not the control file.** 03 checked both `smt/control` = `off` and that online CPUs actually dropped (384→192). **Laptop:** assert 16→8 online and exactly CPUs 0,2,…,14 remain; fail otherwise. (README diff row 5)
- **Branch on live sysfs state, not the recorded prior value.** On a re-run, `PRIOR_SMT=on` against hardware already off sent 03 down the write path; the count check saw 8→8 and failed for having nothing to do. **Laptop:** decide every set step from live state. (`78c2528`)
- **Revert record: write once, atomically, never overwrite.** 03 builds `prior_config.env.partial` and `mv`s it into place; a re-run preserves the existing record; a truncated record stops the phase for a human; 08 deletes it only after a successful restore. **Laptop:** same — an overwritten record is the only copy of the machine's original state, lost. (`78c2528`)
- **Read the governor from sysfs, not cpupower's prose.** `PRIOR_GOVERNOR` was parsed from the wrong `cpupower` field and recorded the literal `use`, so every revert failed. **Laptop:** read `scaling_governor`, strip whitespace. (`77089f3`)
- **Revert can only restore what was recorded.** S's record predates `bpf_stats_enabled`, so 08 reported it could not restore it. **Laptop:** record every knob ever touched from day one — SMT, boost, governor, EPP, platform profile, `perf_event_paranoid`, `bpf_stats_enabled`, `perf_event_max_sample_rate`, TLP/smartd/irqbalance state, slice cpusets, IRQ affinity — and validate the key list against what the revert reads. (SERVER-NOTES §7, `78c2528`)
- **Failure-isolated revert steps.** Under `set -e` one failing restore aborted 08 and left later settings changed. Each step is now isolated. **Laptop:** same. (`0a01f3d`, 08 header)
- **Derive cpusets from `lscpu -e`; don't hard-code.** Online only, one CPU per physical core (lowest-numbered thread), disjoint sets, re-read after the SMT change. **Laptop:** derive, then assert the result is `0,2,4,6` / `8,10` / `12,14`; siblings here are (2k, 2k+1). (00_lib.sh `derive_cpusets`, [CLAUDE.md](CLAUDE.md))
- **The headroom rule is overridden on purpose.** S's derivation refuses 4+2+2 on an 8-core machine because no core is left for kernel, sshd, dockerd or the orchestrator. **Laptop:** this was consciously overridden by putting OS and IRQs on 12,14 — keep that written down, and remember wrk2/memtier then share cores with system daemons. (00_lib.sh header, `7bf19cf`)
- **L3 placement differs from S's isolated arm.** S's isolated arm put workload, tracer and generator in one L3 domain and still measured ≈0 overhead, so sharing L3 was never shown harmful. The laptop puts the workload alone on CCX0 and tracer + generator on CCX1, which changes the cache path between workload and tracer buffers. **Laptop:** record it as a layout property. (GEN2 docs, [README.md](README.md))
- **`perf_event_paranoid`: probe that it can be lowered; don't fail on its current value.** The old laptop tree's 01 hard-fails when paranoid > 1; the laptop ships at 4, so it would abort before 03 lowers it. S probes that the write to -1 takes and restores it. **Laptop:** same. (README diff row 3; `docs/drafts/nginx-perf-pipeline-laptop/01_preflight.sh:103`)
- **Disable unattended-upgrades and record its state.** A silent kernel bump breaks BTF/CO-RE matching mid-project. The snapshot keeps "unit not found" (empty) distinct from "disabled". **Laptop:** disable it and snapd refresh. (03, README snapshot section)
- **Snapshot machine state before and after; diff.** S records 25 fields classed critical / volatile / informational, warns rather than fails, and separately warns about a critical field empty in both snapshots. One pre/post pair brackets the whole invocation — and `run_scope_levels.sh` skipped it, so the eBPF isolated arm has no drift record. **Laptop:** snapshot under every driver, ideally per cell; temperature and RAPL are evidence here, not decoration. (`7a244c4`, GEN2-ebpf provenance)

## Workload and load generator (wrk2, nginx, rate calibration, co-location)

- **Co-location is a biased estimate, not a bound; the direction depends on the mechanism.** With wrk2 on the tracer's 2 cores, perf wide p999 read +12/+20/+49/+2769%; isolated, −0.24/−0.35/+0.82/+3.93%. eBPF narrow E4 read −11.64% co-located vs −1.35% isolated. **Laptop:** the 4+2+2 layout is right; never call a co-located number conservative. (GEN2-ARM-RESULTS-S.md, GEN2-ARM-RESULTS-ebpf-S.md, `beda8d9`)
- **`loadgen_cpu_cores` is necessary, not sufficient.** It caught the starved perf E4 cell (0.8883 vs 0.9858 cores) but passed perf E1–E3, which were inflated by 12–48 points; for eBPF it fired on exactly the understating cells. **Laptop:** record it every run, compare traced vs bracket mean, read it against the generator cpuset's capacity; a pass is not "clean". (`../docs/plan/measurement-analysis.md` §1)
- **The ladder's ceiling was wrk2's, not nginx's.** Baseline p99 went 1.81 ms at 5k → 1.75 s at 140k with `-t2 -c100`; at `-t4 -c400` p99 was 26.4 ms and nginx used 36% of its cores. **Laptop:** run a laptop pilot ramp (S's 10k/20k/40k/80k is only a default), log generator CPU at each point, never call the top level "near nginx's capacity". Same question open for fio and memtier. (SERVER-NOTES §4.5, `800b1c7`)
- **One generator configuration across every cell and mechanism.** S used `wrk2 -t2 -c100 -L` everywhere. **Laptop:** pick `-t/-c` once from the pilot, freeze and record it; ramp and measured invocations both pinned to generator cores. (04)
- **The ramp is a separate, unmeasured invocation.** Originally the 30 s ramp sat inside the measured window (`DURATION_S=150`), diluting every metric. Now: ramp with no tracer, attach tracer, then measured wrk2 for 120 s. **Laptop:** keep the split. (`bd7e107`)
- **`-L` is mandatory; latency units vary.** HdrHistogram prints `593.00us`, `2.1ms`, `1.75s`; a parser stripping only `ms` produced 1000×-wrong values. Convert us/ms/s explicitly, fail on anything else. **Laptop:** same parser, with fixtures from real laptop output. (`bc99342`)
- **Constant-rate generator ⇒ overhead shows in latency, not throughput.** Throughput moved ≤0.37% in every cell; tails carry the signal. **Laptop:** same for wrk2 and fixed-rate memtier. (all MATRIX docs)
- **wrk2 under pipefail.** `wrk2 --version` prints its banner and exits 1, so `wrk2 | grep -q` fails, and a version-capture pipe died of SIGPIPE (141). Fix: capture into a variable, `|| true`, emptiness check as the real guard. **Laptop:** already hit in `install_build.sh`; keep the pattern. (`83ce006`, [README.md](README.md))
- **Pin nginx worker count and affinity.** `worker_processes 2`, never `auto`. `worker_cpu_affinity` bitmasks put CPU 0 at the rightmost bit with absolute CPU numbers (laptop CPUs 0 and 2 → `0001 0100`); fail on any unsubstituted placeholder. **Laptop:** 2 workers leave 2 of 4 workload CPUs idle while wide `-C` traces all 4 — decide deliberately (S did it unremarked). (04, config.env, 00_lib.sh `cores_to_affinity_mask`)
- **Narrow scope must target the workers, not the master.** perf `-p` inheritance only follows children forked after attach; targeting the master profiles an idle process and reports zero cost. Resolve `pgrep -P <master>` after the ramp, assert the count equals the worker count, give the same PID set to perf and BCC. **Laptop:** same. (`77089f3`, 04)
- **Docker hygiene.** Remove a stale container by name before `docker run`; check `.State.Running` before trusting `.State.Pid` (a port collision shows as PID 0); get the nginx version with `--entrypoint nginx` (entrypoint chatter was once recorded as the version). **Laptop:** same. (`83ce006`, 04)
- **Docker's cgroup path depends on the cgroup driver.** systemd: `system.slice/docker-<id>.scope/cpu.stat`; cgroupfs: `docker/<id>/`. Hard-coding one aborted run 1. **Laptop:** systemd driver, but probe both and fail hard on a miss. (04 `resolve_cgroup_cpu_stat`)
- **INFERENCE — load may go through docker-proxy.** S published `-p 127.0.0.1:8080:80`, and nginx saw the collector's scrapes arrive from 172.17.0.1 — consistent with docker's userland proxy relaying loopback traffic, which would carry all of wrk2's 80k rps through an unpinned docker-proxy process. On S that landed on 186 idle cores, unmeasured. **Laptop:** no idle core exists; check with `ps`/`pidstat`, then use `--network host`, disable `userland-proxy`, or pin and measure the proxy. (inference from SERVER-NOTES §4.9)

## perf

- **`perf trace` drops most events at the default buffer.** ~94% lost at 5k rps; 3.6–30.4 M events lost per run across E1–E4. `-m 16384` reached 0% loss but took 17.6× the window to drain (~33 min per 120 s run, 5–6 h per cell). `perf record` with `-m 512` lost nothing. **Laptop:** set and record `perf trace`'s buffer, or drop `perf trace` and say so; always report its loss count. (FIRST-RUN-RESULTS, `8eea414`)
- **A saturated `perf trace` looks cheap.** Its ~1.0-core cost is a lower bound twice over: most work was dropped, and the post-window drain falls outside the tracer-CPU poller bounded at `STEADY_SECONDS+60`. **Laptop:** bound the poller to cover teardown, or report drain separately. (FIRST-RUN-RESULTS)
- **Use `--summary` with `perf trace`.** Per-event text output loaded the cores shared with the generator; `--summary` still attaches to every syscall. (`77089f3`)
- **Matched wide scope is `-C <workload cpuset>`, never `-a`.** `-a` opens one buffer per online CPU and changes what is measured. (04 header, SCALE-ARM-RESULTS-S.md)
- **Parse `perf report --stats` correctly.** Real lines are `LOST events:` and `LOST_SAMPLES events:`; the old parser grepped `PERF_RECORD_LOST`, which perf never prints, and the fixture invented the same string. Missing LOST line = 0 (perf prints only record types present). Match whole fields so `LOST` ≠ `LOST_SAMPLES`. Take the first `SAMPLE events:` (repeats per selector). Missing file is fine on a baseline; unparseable is a failure. (00_lib.sh `extract_perf_*`, `77089f3`)
- **Sum `perf trace` loss notices.** Lines read `LOST N events!`, repeating per episode and per CPU; match unanchored (color_fprintf). (00_lib.sh `extract_perf_trace_lost`)
- **The kernel lowers `perf_event_max_sample_rate` by itself.** On S it fell 100000 → 73000 when sampling exceeded `perf_cpu_time_max_percent=25`, also producing THROTTLE/LOST_SAMPLES. **Laptop:** record both sysctls before/after every run (or pin them); record LOST_SAMPLES separately from LOST. (SERVER-NOTES §4.2)
- **`-g` was frame pointers on S, not DWARF.** 218 B/sample with `-g` vs 8606 B with `--call-graph=dwarf`; short captures mislead because of the ~1 MB header. **Laptop:** perf 7.0.14 is a different build — re-measure before sizing disk. (SERVER-NOTES §4.3)
- **`perf stat -C` task-clock is useless as in-line CPU.** It reads wall time × CPUs, a constant; an explicit `-e` list drops task-clock unless named. **Laptop:** in-line CPU comes from the workload cgroup's `usage_usec`. (`86efa4d`, `bd7e107`)
- **Stop perf with SIGINT, never SIGKILL**, so `perf.data` flushes. Run `perf report --stats` before compressing; compress (zstd, gzip fallback) only after stats parse. (04)
- **Record perf vs kernel version.** S ran perf 7.0.2 on kernel 6.8 (`perf_kernel_match=false`), accepted because both arms used the same binary. **Laptop:** 7.0.14 on kernel 7.0 matches; still record it. (README "Known, accepted")

## eBPF / BCC

- **BCC attaches system-wide, then filters in the kernel.** The cpuset/PID restriction is a comparison inside the program; on S it discarded 15.7 events per one kept at wide scope (20.3:1 isolated) and 2.0:1 narrow, mostly wrk2's syscalls. Count discards per run (`EBPF_KERNEL_FILTERED`). **Laptop:** ratio should be far smaller on 8 CPUs; report it per arm — it depends on what else the box does. (SERVER-NOTES §4.6, `ebpf/nginx_probes.c` header)
- **BCC userspace cost scales with event rate.** 0.11 → 0.76 cores over 10k→80k, ~3.5–5.4 µs per delivered event in the Python callback. Keep the callback to increment-and-return. **Laptop:** two tracer cores should hold; watch tracer-cpuset utilisation at the top level. (MATRIX-RESULTS-nginx-ebpf-S.md)
- **Fixed perf buffer, 512 pages per CPU** — same unit and number as `PERF_MMAP_PAGES`; 0 lost at 212k events/s. Allocation is per online CPU (16 MiB on the laptop, ~400 MiB on S); don't equalise. Zero drops is a property of this configuration, not of the mechanism. (config.env)
- **Wait for attach before opening the window.** Clang compile takes ~1 s. `bcc_tracer.py` writes a ready file only after probes attach; 04 polls with a 60 s timeout, deletes stale ready files first, fails if the tracer dies before ready. **Laptop:** same; BCC 0.35 vs S's 0.29.1 needs one real run first. (04, SERVER-NOTES §4.6)
- **Guard against a tracer that saw nothing.** Fail the run if the kernel submitted zero events while wrk2 served requests; the BPF source `#error`s without a scope `-D` flag. Either would otherwise read as "eBPF is free". (06, `ebpf/nginx_probes.c`)
- **Stats file whose last key marks completion.** `bcc_tracer.py` writes `EBPF_EXIT=ok` last: missing = truncated, non-ok = interrupted; both refused. Every key written every run; a missing key is a defect, never zero. (04, 06)
- **BPF JIT checks.** Hard-fail on `bpf_jit_enable=0` (interpreter ~10× slower); warn on nonzero `bpf_jit_harden`; record both, never write them. (01, README)
- **`bpf_stats_enabled=0` in main arms.** It charges per program run and the baseline attaches none, so the cost survives A-B-A subtraction. Consequence: eBPF's in-kernel CPU is unmeasured; the tracer-CPU column is the userspace poller only. **Laptop:** to measure it, a separate arm with stats on in both bracket arms; record and restore the sysctl. (config.env, `../LEARNING.md`)
- **Check CPU ids against the filter array size.** An id ≥ array length silently reads as "not traced". **Laptop:** ids reach 14; size the array ≥ online CPU count. (`ebpf/bcc_tracer.py`)

## Collector (otelcol)

- **An nginx allow-list zeroed the whole collector arm.** `/status` had `allow 127.0.0.1; deny all;`; scrapes arrive from 172.17.0.1 via the docker bridge, so nginx answered 403 and every counter was zero while run, bracket and drift checks all passed — one line in `otelcol.log` was the only trace. Fixed by removing the allow-list and adding an `accepted > 0` ingest guard. **Laptop:** keep the guard; grep `otelcol.log` for non-200s every run. (`ae39e82`)
- **Charge the collector's own PID, not the wrapper's.** CPU from `/proc/pid/stat` fields 14+15 (utime+stime), children excluded. The wrapper sleeps: charging it read 0 ticks while otelcol went 419 → 936. `otel_tracer.sh` writes otelcol's PID via `--pid-file`. **Laptop:** same rule for any wrapper-launched tracer. (SERVER-NOTES §4.9, `a390ff8`)
- **otelcol 0.161.0 config facts.** Receivers `nginx`/`hostmetrics`. `service.telemetry.metrics.address` is removed — use `readers: - pull: exporter: prometheus:`. `level: detailed` is required or per-component metrics are absent. No `_total` suffix. `otelcol_processor_refused_metric_points` and `otelcol_processor_dropped_spans` do not exist. The `debug` exporter accepts `sending_queue`; `file` rejects it. **Laptop:** same pinned version; 01 must fail on a version mismatch, since a renamed metric silently empties columns. (SERVER-NOTES §4.9)
- **Two absences mean opposite things.** A counter absent from Prometheus output = zero (never incremented); a key absent from your own stats file = defect. Difference counters between a baseline and final read so they describe the window, not process lifetime. (`sidecar/otel_tracer.sh`)
- **Scraped ≠ accepted.** 60 scraped vs 105 accepted; 1120 vs 4921. Never substitute one as the other's denominator. (SERVER-NOTES §4.9)
- **Run otelcol as a pinned host process with the `debug` exporter** — not a container (CPU accounting matches perf/BCC), no sink process (its CPU would be unattributed). Telemetry on 127.0.0.1:18888, fixed non-default port so a leftover collector can't be read instead; 01 checks it is free. RSS ~203 MB. **Laptop:** same. (README diff row 11)
- **Serve `/status` (stub_status) in every run under every mechanism**, so the workload is identical; accept that scrapes add a few requests to nginx's in-line CPU. (`a390ff8`)
- **The scraper arm is rate-invariant.** Cost tracks scrape interval × receiver count, so it is excluded from crossover claims (06 stamps a note into every scraper row). Narrow (15 s, 1 receiver) 0.0002 cores; wide (1 s, nginx + 8 hostmetrics scrapers) 0.20–0.24 cores and ~2× p999 at only 17–59% cpuset use — not saturation, but co-located and never isolated. **Laptop:** 4+2+2 gives the isolated measurement S never got. (MATRIX-RESULTS-nginx-collector-S.md)
- **The scope step changes two things.** Receiver count 1→9 and interval 15→1 s together, so the effect can't be attributed. An OTLP arm needs a span source in nginx *and* span-scoped counters in stats file, schema and collection step in the same edit, or it counts zero spans while looking complete. **Laptop:** plan the disambiguation arm and OTLP counters up front. (root CLAUDE.md, `a390ff8`)
- **Pin tool versions; don't discover them via the GitHub API.** Rate limits produced an empty version, a 9-byte 404 page, and "gzip: not in gzip format". **Laptop:** already pinned; verified against the per-artifact `.sha256`. (SERVER-NOTES §4.8, [README.md](README.md))

## Measurement and metrics (CPU attribution, drops, A-B-A, drift, statistics)

- **Three CPU figures, never conflated.** (1) System busy% from `/proc/stat` — near-useless across 192 CPUs on S, meaningful on the laptop where 4 of 8 CPUs are workload. (2) Pinned tracer CPU from the tracer PIDs' `/proc/pid/stat` tick deltas. (3) In-line CPU from the workload cgroup's `usage_usec` delta, recorded on baselines too for differencing. Never compute (2) from the cgroup. (`../docs/plan/measurement-analysis.md` §1, `bd7e107`)
- **End-of-window CPU needs a background poller.** A direct end read failed because processes had exited. Use the last complete sample (written only after every PID was read; stop when any PID is gone); require ≥2 samples, or one sample returns the start value as a fake 0.0000; read start ticks right after launch; record `CLK_TCK` every run. (04, 00_lib.sh `last_complete_sample`)
- **Pin every sampler and poller.** S: aggregator cpuset; loadgen poller on the generator cores. **Laptop:** decide where samplers live (tracer 8,10 or OS cores 12,14) and apply identically in both arms. (04)
- **Close the measured window before teardown.** The `/proc/stat` sampler once ran through `perf report`, giving traced runs a longer busy% window than baselines. Stop samplers, take timestamps and cgroup snapshots before detach/report. (`77089f3`, 04)
- **Drop-rate denominators differ by mechanism.** perf: LOST / (LOST + SAMPLE); BCC: lost / `expected_events`; collector scraper: n/a. Only trends compare across mechanisms, not levels. Never report overhead without its paired drop rate — a saturated tracer looks cheap. (`../docs/plan/measurement-analysis.md` §1)
- **INFERENCE — the drift check is weak under a constant-rate generator.** 05 judges A1/A2 drift on throughput, which fixed-rate wrk2 pins, so it passes trivially (all S drifts ≤0.37%). In the first collector cell A1/A2 p99 differed ~10% (1.82 vs 1.65 ms) and the bracket passed at 0.368%. **Laptop:** judge drift on p99 and/or baseline CPU, not only throughput. (05_orchestrate_cell.sh:278–282, SERVER-NOTES §4.9)
- **One A-B-A bracket per cell.** 3 warm-ups, A1, 6 traced, A2 = 11 runs; bracketing every rep (21 runs per cell) was a real bug. Drift threshold 5%; a failed bracket reruns the whole bracket. Keep n=6 (Wilcoxon floor). (`77089f3`, `../LEARNING.md`)
- **Negative latency deltas are diagnostics; report spread.** A traced run cannot be faster than its baselines. Isolated eBPF rep-to-rep p999 spread was 1.7–12.3%. **Laptop:** report the traced reps' spread beside every delta; only 2 baselines anchor each cell. (GEN2-ebpf, `../docs/plan/measurement-analysis.md` §1)
- **What the null result means.** Isolated, perf (~1.0 core flat wide, 0.0036 narrow) and BCC (0.11→0.76 cores) imposed ≈0 on nginx's tail at 10k–80k; the crossover is in tracer cost, not workload impact. Tracing all 192 CPUs showed cost only in tail latency, not tracer CPU. **Laptop:** never measure tracer CPU alone. (DATA-REPORT-S §3, SCALE-ARM-RESULTS-S.md)
- **Per-row diagnostics in `run_notes`; silence means clean.** Drops, filter discards, clock verdict, `perf trace` loss, scraper caveat, bpf_stats-on. A note on one side of a bracket is itself a signal; add a note when a check could not run. (06)

## Pipeline engineering (run IDs, revert on failure, `set -u`, testing, disk, retention)

- **The old laptop tree has known aborts.** Its 03 uses `$WORKLOAD_CORES` without sourcing `state/cpusets.env` (aborts under `set -u`); its 01 aborts on paranoid > 1; it drifted ~2100 lines behind S. **Laptop:** source everything a script reads, keep shared constants in one sourced file, do one real run of each script before trusting it. (`7bf19cf`, [CLAUDE.md](CLAUDE.md))
- **Sourced env files clobber variables.** 06 sourced each bundle's `run_meta.env`, whose `SCOPE` overwrote the requested scope, so both scopes landed in one file. Suffix run-time keys (`*_USED`), use script-owned names (`CELL_SCOPE`). (`18e16c6`, 04)
- **Deterministic run IDs encoding every factor.** `<platform>_<workload>_<scope>_E<level>[_ebpf][_gen2]_cell_tryN_{A1,BN,A2}`; storing fails on collision instead of duplicating rows. Ingest filters each bundle on its own recorded fields (MECHANISM, CPUSET_LAYOUT, level), never directory names. **Laptop:** per-pair folders help, but keep the fields in metadata. (05, `22ce69d`, `7bf19cf`)
- **No defaults for factors; rate from a level, never a raw rate.** `--rate-level` is required and maps through `EVENT_RATE_LADDER`. Mechanism is a config key, not a flag, so one fact never has two sources (an earlier mismatch produced a silently empty cell). (config.env)
- **An abort leaves the host configured.** S's orchestrator aborts without reverting; `--revert-only` is the recovery path. **Laptop:** trap that reverts on failure. Inside a run, an EXIT trap removes the container, kills wrk2 (an orphan kept driving load), SIGINTs tracers, writes an `INCOMPLETE` marker ingest skips. Bound every `while` loop — SIGKILL skips traps. (04 cleanup, [CLAUDE.md](CLAUDE.md))
- **Fail hard over blank columns.** A traced run missing drop stat, tracer CPU, cgroup cpu.stat or loadgen CPU is not a data point. 06 checks every row has 36 fields, counted quote-aware (cpusets contain commas). (`b6b06d1`, 06)
- **Frozen schema contract.** `schema.json` records versions, topology, buffers, layout; 07 hard-fails if a new schema differs from the stored one; a different layout or mechanism gets its own CSV and schema. Don't "fix" frozen text inside the schema heredoc. (07, `f36019a`)
- **Unit tests prove logic only.** S had 548 assertions via PATH-injected stubs, and a fixture invented a perf string so a test passed against fiction. **Laptop:** fixtures from real laptop tool output; green suite ≠ works on hardware. (`77089f3`)
- **Windows checkouts break scripts.** `git archive`/`autocrlf` emit CRLF (`$'\r': command not found`); extensionless stubs break; files arrive without the exec bit. **Laptop:** strip `\r`, run `sudo bash ./x.sh`, commit with `--chmod=+x`. (SERVER-NOTES §5, [README.md](README.md))
- **Check free space at preflight and every run.** A full disk truncates `perf.data`, and `perf report --stats` parses a truncated file happily. The 88-run matrix took ~263 MB with zstd. **Laptop:** 61 GB on `/var/tmp` is plenty; the bigger disk risk is fio vs QLC SLC exhaustion. (README free-space section, SCALE-ARM-RESULTS-S.md)
- **Measured time budgets (S).** One run ~2.5–3 min; one cell 28–33 min; 8-cell matrix ~4.5 h; pilot ramp ~12 min. (SERVER-NOTES §6)
- **Server-only, minor:** `pgrep -f`/`pkill -f` match your own SSH command line; long jobs need `systemd-run --unit=… --collect` to survive SSH; transfer one tarball, not many files; needrestart bounced systemd-resolved mid-apt (just re-run). **Laptop:** relevant only if driven over SSH.
